## 判官总结

三个视角独立收敛到同一结论：**架构主线健康（Op-as-data、毒化契约、oracle 同构、双工具链锚点全部真实有效），但 M4 作为承诺层诞生之地，其上的语义承诺有一个说谎、运行时入口是断的、两个算子的语义覆盖是空的。** 这些不是风格分歧，是可以逐条复现的事实。分歧点仅在严重级与修复时机：

- binary-op other：三人一致 blocker（Carmack/Hickey 从各自角度独立升级第一层的 warning）。修复方案分歧（真实 handle id vs throw-until-M5）：判官裁决取**方案 A（真实 handle id 进 Op + runChain 解析）**——protocol.ts 的 other: HandleId 是 design §5.1 既定形状，方案 B 把公开 API 的 throw 债务转移给 M5 wire path 且 DX 更差；M5 反正要在同一 Op union 上建 wire，本里程碑修完并补 distinct-operand 金样即在同一门内闭合
- extraction 泄漏：三人量化一致（Carmack 给出 48MB/次 + M5 1GB 级驻留；Hickey 补充 sync 长寿命实例同样中招；我实测 +68MB/60 次）。判官裁决**本门必修**——修复是 10 行 cpp + CI 重编译，且必须在 M5 worker 测试基线建立之前落地，否则泄漏被烤进测试基线
- Node 入口（Hickey 独有发现，Carmack/Beck 均未覆盖）：判官裁决 **blocker 成立、本门必修**——Node 是 PRD 决策 ⑫ 一等公民目标，「import 即失败」+「无测试能发现」的组合在发布门 M6 前无法自愈（M5 worker 也不走这个入口）。修复取 emit JS 路线（gen-types.mjs 已在跑 tsc，emitDeclarationOnly 改掉或加独立 emit 步骤），import 指向 dist/index.js；同时 consumer check 追加 node main.ts 执行（Beck W4 同根，一行修两个 finding）
- deskew/findSkew 退化锚点（Carmack 独有发现）：判官裁决 **warning、本门必修**——PRD 算子清单两个算子的语义覆盖目前是零（三条金样链全是 passthrough），且修复已被 constructive proof 验证可行（斜带 fixture 约 15 行）。这不是「覆盖不足」而是「承诺的算子从未被测过语义」
- 红→绿偏差（Beck W1）：判官裁决**如实记录进本文件（已录），M5 起新算子单算子红→绿对提交**——不回溯重写历史（归档 CI run 是真实红证据），纪律前移
